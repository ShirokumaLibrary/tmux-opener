**英語版 `font-packages/README.md` が `providedFont` 契約の単一正本である** ——
*フォントリソース拡張機能*
が *消費側拡張機能* の webview にフォントを供給するための規約がそれである。`font-packages/`
配下の各 package は **その package 自身のフォント** についての事実(どの face を出荷するか・
バイト列がどこから来たか・family 名が何と実測されるか)を記録する。契約の *形式*・読み手の
正規化・縮退の規則は、ここに書かれ、ここ以外には書かれない。

なぜここか: `font-packages/` は `export-ignore` されていないので、この文書は公開リポジトリと
第三者の消費側に届く。かつ **どの VSIX にも同梱されない** —— フォント拡張機能は *それ自身の*
ディレクトリからパッケージされ、tmux-opener 本体は `.vscodeignore` で `font-packages/**` を
除外する(`scripts/verify-vsix.js` が表明する)—— ので、仕様を改訂しても何かを再公開する
義務は生じない。契約仕様と拡張機能のリリースサイクルは意図的に切り離してある。

**VS Code に拡張機能間でフォントを共有する公式の仕組みは存在しない。** 以下は供給側と消費側の
間で取り決めた非公式・自前の規約である。片側だけ契約の形を変えると、消費側は **無音で** 壊れる。

以下の参照がバッククォート付きの素のパスであって Markdown リンクでないのは意図的である:
これらの README は VSIX に同梱されて Marketplace 上でレンダリングされ、そこでは `vsce` が
相対リンクを書き換える。クリックできることより、壊れないことのほうが重要である。

## 契約フィールド

フォントリソース拡張機能は、自身の `package.json` のトップレベルに `providedFont` を宣言する:

| フィールド | 必須 | 意味 |
|---|---|---|
| `family` | はい | このフォントが名乗る CSS の family 名。**消費側はこれを注入に流し込まない** —— 消費側は自分が保持している family 文字列を宣言し、こちらの値をそれと突き合わせる(「注入機構はフォントファイル内部の名前に依存しない」を参照)。 |
| `faces` | 2 つの宣言形のいずれか | `{ file, weight }` の配列。出荷する face ごとに 1 エントリ、宣言順。 |
| `file` | 2 つの宣言形のいずれか | 1 つの face のフォントファイルのパス。拡張機能ルートからの相対、区切りは `/`。 |
| `weight` | フラットな `file` の隣では任意(規則 3 を参照)。`faces` エントリ内では必須 | その face の CSS `font-weight` ディスクリプタ値。フラットな `file` の隣で省略すると既定 `100 700`、`faces` エントリ内で省略するとそのエントリごと落ちる。常に明示して書くこと。 |
| `license` | はい | フォントのライセンスの SPDX 識別子(例 `OFL-1.1`)。**情報提供のみ —— 消費側のコードはこの値を読まない**(tmux-opener の契約 *型* は `license?: string` を宣言しテストの fixture も設定するが、`src/` にも `test/` にもこのフィールドを読む箇所はない)。借用するかどうかを判断する人間に条件を伝えるためのものであり、ライセンス本文そのものは package に同梱される。 |

`family` と `license` はどちらの宣言形でも face の宣言の外に置かれる。変わるのは *face* の
宣言のしかただけである。

### 宣言形 A —— `faces[]`(N 面)

```json
"providedFont": {
  "family": "Mgen+ 1mn Term",
  "file": "fonts/MgenPlus1mnTerm-Regular.ttf",
  "weight": "400",
  "faces": [
    { "file": "fonts/MgenPlus1mnTerm-Regular.ttf", "weight": "400" },
    { "file": "fonts/MgenPlus1mnTerm-Bold.ttf", "weight": "700" }
  ],
  "license": "OFL-1.1"
}
```

ここで `faces` の隣にあるフラットな `file` / `weight` は **宣言形 A の一部ではない** ——
`faces` 配列だけで完結した正当な契約であり、読み手は `faces` が配列であるかぎりフラットな
対を無視する。これが書かれているのは、*このリポジトリ* の package が古い読み手のために常に
フラットな別名を残しているからで、それはリポジトリ側の作法(後述「フラットな別名は常に残す」)
であって、あなたに課される要件ではない。

### 宣言形 B —— フラットな `file` / `weight` の対(1 面)

```json
"providedFont": {
  "family": "Some Variable Mono",
  "file": "fonts/SomeVariableMono.ttf",
  "weight": "100 700",
  "license": "OFL-1.1"
}
```

フラットな対は **1 face の短縮形** であり、恒久的にサポートされる: `faces` が存在する前に
書かれた消費側が、`faces` を持つ契約に対しても無改造で動き続ける(フラットな face だけを
得る)。両方を保つ意義はまさにそこにある。

この例が意図的に **架空の可変フォント** になっていて、その理由が `weight` である。`100 700` は
本当にその軸を持つ face についてだけ正当な宣言であり、静的な face の上では後述「静的 face は
単一値を宣言する」で説明する合成 bold 抑止の罠になる。この枠にはかつて実在の
`font-mplus1code` の契約が入っていた —— まさにそういう可変フォントだった —— が、#275 が
それを 2 つの静的 face にインスタンス化した時点で、正本の文書が「もう軸を持たない package」を
使って罠を教えることになってしまう。**このディレクトリのどの package も、もう範囲を宣言して
いない**。出荷される face はすべて静的で、単一値を明示している。

### どちらの宣言形が優先されるか

**配列である `faces` キーが正である —— 空配列であっても、全エントリが不正であっても。
フラットな対が読まれるのは `faces` が配列でないときだけ** —— これはキーが存在しない場合・
`null` の場合・配列でない truthy な値の場合を等しく含む。

- 判定は `Array.isArray(contract.faces)` である。`contract.faces ?? [...]` は **誤り**:
  配列でない truthy な値(オブジェクト・文字列)は face のリストとして走査されるのではなく、
  フラットな対にフォールバックしなければならない。
- この非対称は意図的である。`faces` 配列が使えないと分かったときにフラットな対へ
  フォールバックすると、壊れた複数 face 宣言が余分な face を *無音で* 失う —— bold が単に
  描かれなくなる。何も返さなければ family は「供給元なし」へ送られ、消費側はそれを表明できる
  (tmux-opener ではインストールの促し)。誤ったものを見せるくらいなら何も見せない。

## 正規化(読み手が計算しなければならないこと)

参照実装は tmux-opener の `src/font-registry.ts` の `normalizeContractFaces` であり、
本節はその仕様である。

1. **契約そのものが無い**(`providedFont` が存在しない)→ face なし。
2. **`faces` が配列である** → *妥当な* エントリだけを残して宣言順に写像する。エントリが
   妥当なのは `file` と `weight` が **両方とも** **空でない文字列** であるときだけである。
   - **文字列であることの要求は、存在の要求ではなく型の要求である。**
     `{ "file": "fonts/x.ttf", "weight": 700 }` —— 文字列 `"700"` ではなく JSON の *数値* ——
     は **不正** であり、配列・オブジェクト・`null`・`true` として与えられた `file` も同様である。
     エントリは **まるごと** 落ちる。読み手は数値を文字列へ変換しないし、不正な `weight` を
     捨てて `file` だけ残すこともしない。すべての値を JSON の文字列で書くこと。
   - **`faces` の内側に weight の既定値は存在しない。** `weight` を省いたエントリは既定値を
     得るのではなく落ちる。複数 face のリストの中で weight を宣言しない face は、*それがどの
     face なのか* を何も言っていない。
3. **`faces` が配列でない** —— 存在しない・`null`・配列でない任意の値 —— → フラットな対を読む。
   `file` は空でない文字列でなければならず、そうでなければ face は無い。`weight` は、存在
   しない・空・文字列でないときに **`100 700`** を既定値とする。
   - **この既定値はフラット形専用である。** これは、ここで公開された最初の単一ファイル可変
     フォント契約 —— #275 以前の `font-mplus1code`、その fvar 軸は本当に 100–700 だった ——
     のために存在する。#275 以降その package は 2 つの静的 face であり、**出荷中のどの package も
     もうこの既定値に依存していない**。残してあるのは、それが公開済み契約の一部だからであって、
     同梱の face がまだその軸を持っているからではない。これは face 一般についての言明ではなく、
     上の規則 2 はこれを適用しない。**静的な** face がこれを継承すると、持っていない範囲を
     無言で宣言することになる —— 後述「静的 face は単一値を宣言する」を参照。ここの各 package が
     `weight` を明示しているのはそのためである。

結果は `{ file, weight }[]` であり、以降のすべての工程が見るのはこれである。正規化より後で
`contract.file` や `contract.faces` を読み直す箇所はない。

## 縮退(family を供給できないとき)

2 段階あり、意図的に異なる縮退のしかたをする。

### 宣言段階 —— 400 の規則

正規化のあと、**少なくとも 1 つの face が weight 400 を覆っていなければならない**。400 は
ターミナルが普通のセルに対して要求する重みであり、借用したバイト列から通常の本文を描けない
family は、そもそも提供してはならない。

400 を覆う face が 1 つも無い場合(face が 0 個の場合を含む)、**その family 全体** が供給元を
持たない: 消費側はその family について **`@font-face` を一切注入せず**、CSS のスタックは OS の
標準等幅へ抜ける。部分的な集合を注入することはしない。

**400 を覆うかどうかは数値のディスクリプタ値だけから判定される:**

- 単一値 —— `"400"` —— はちょうどその重みを覆う。
- 2 値の範囲、CSS ディスクリプタと同じく空白区切り —— `"100 700"` —— はその両端を含む間の
  すべての重みを覆う。

それ以外は **理解されず、解釈できない主張は主張なしとして扱われる**: 空文字列・3 つ以上の
トークン・数値でないトークン。

> **CSS のキーワードは数に入らない。** `normal` と `bold` は CSS 上まったく正当な
> `font-weight` ディスクリプタ値であり、ブラウザは `normal` を 400 と読む —— が、この契約の
> 読み手は **読まない**。`"weight": "normal"` を宣言する face は規則 2 の意味では妥当(空で
> ない文字列)だが何も覆わないので、`normal` を宣言する face しか持たない family は
> 「供給元なし」に解決される。weight は数値で宣言すること。

### 実在段階 —— face 単位の drop

宣言されたファイルが実際にディスク上にあるかまで確認する消費側は、**ファイルが欠けている
face だけ** を落とす。bold face を宣言しながら regular しか出荷していない package は、family を
まるごと失って OS の等幅へ落ちるのではなく、regular face で描画され続ける —— 従来どおりの
挙動である。family ごと失うのは、パッケージングの手違いに対して壊れた範囲をはるかに超える罰を
与えることになる。

唯一の例外はまた 400 の規則である: 生き残った face の中に 400 を覆うものが無ければ、その family は
まるごと「供給元なし」へ行く。それが、消費側が提供するものの意味(「提供されるどの family も、
借用したバイト列から通常のセルを描ける」)を真に保つ。

**この縮退は意図的に無音であり、実行時にそれを報告するものは何も無い。** bold face を宣言して
regular しか出荷していない package は、bold を一度も宣言しなかった package とまったく同じように
描画される: 警告もなく、通知もなく、ユーザーに見える違いは bold セルがふたたび合成されることだけ
である。リポジトリ側の檻は `npm test`(ソースツリー上で、宣言された全 face をディスクに対して
確認する)であり、ここのどの機械層も確認しないのは **公開された VSIX** が宣言どおりの face を
実際に含んでいるかどうかである —— それはパッケージング時の人の手順である。

**実在確認そのものについて安全上の注意が 2 つある。** これは webview ではなく拡張機能ホストで
走るからである:

- `localResourceRoots` はこれを **守らない**。あのルートは *webview のリソース配信* に対する
  アクセス制御であり、拡張機能ホスト側の `fs` 呼び出しはその外にある。
- `Uri.joinPath` は `..` を **解決する** ので、`.split('/')`(絶対パスの `file` を無害化する
  効果はある)だけではトラバーサルを止められない。宣言されたパスを stat するなら、解決後の
  絶対パスがまだ `fontExt.extensionUri` の内側にあることを確認してから `fs` を呼ぶこと。
  さもなければ `"file": "../../../../etc/shadow"` を宣言する契約が、供給側拡張機能の外側に
  対するファイル存在オラクルにあなたの確認処理を変えてしまう。**tmux-opener もまだこれを
  していないことに注意**: `fontFileExistsInExtension`(`src/extension.ts`)は
  `Uri.joinPath(ext.extensionUri, ...relFile.split('/')).fsPath` を包含判定なしにそのまま
  `fs.existsSync` へ渡している。これは後述の `font-weight` の件と同じ信頼境界の議論
  (供給側は `FONT_REGISTRY` にハードコードされた固定の拡張機能 ID である)で受容されている ——
  **この正本に照らせば同じく未達である** —— そしてこの 2 点だけがそういう箇所であり、どちらも
  実装済みに見せかけて放置するのではなくここで開示している。

## 静的 face は単一値を宣言する。範囲を宣言してよいのは可変フォントだけ

`font-weight` ディスクリプタは face についての **主張** であり、CSS の font matching は要求された
重みを覆うディスクリプタを持つ face を *本物として* 選ぶ —— その上に合成をかけることはしない。
したがって `100 700` を宣言する **静的な** regular face は bold セルに選ばれ、regular の太さで
描かれる: 範囲宣言は合成 bold を生むのではなく **抑止する**。

- 静的な face は自身の単一の重みを宣言する: regular なら `"400"`、bold なら `"700"`。範囲は
  決して書かない。
- 可変フォントは実在の軸を宣言する(fvar の wght 軸が本当に 100–700 にまたがる face なら
  `"100 700"`)。その範囲はバイト列についての真の言明である。**このディレクトリに今日
  可変な package は無い**: `font-mplus1code` がそうであり、この規則が引いていた実例でもあったが、
  #275 が静的な 400 / 700 face へインスタンス化した —— 変換は可変フォントの輪郭を `gvar` の
  デルタを壊さずには編集できないので、リフィットの前に軸を落とすほかなかった。それでも規則は
  残す。これは宣言が何を意味するかについての規則であって、たまたま何が同梱されているかに
  ついての規則ではない。
- したがって、本物の bold が欲しい family は本物の 700 face を出荷し、それを 2 つめの `faces`
  エントリとして宣言する —— 700 を覆うのは主張ではなくグリフである。
- **可変フォントのインスタンス化では、重みだけでなくスタイルのビットも動かさなければならない**:
  `instantiateVariableFont` は `usWeightClass` を更新するが `OS/2.fsSelection` と `head.macStyle`
  は既定インスタンスの値のまま残すので、bit 5 を立てて bit 6 を落とす何かが無いかぎり bold
  インスタンスは REGULAR を名乗り続ける。`scripts/font-fit/fit.py` がまさにこの理由でスタイルから
  それらのビットを導出している(#275)。ここでの描画はそれらに依存しないが、他の消費側における
  OS レベルのスタイルリンクは依存する。

## 消費側の手順

1. **供給側拡張機能を引く。**
   `vscode.extensions.getExtension('<publisher>.<name>')` は、インストール済みの拡張機能に
   ついては **アクティベートされていなくても** メタデータ(`extensionUri`・`packageJSON`)を
   返す —— `activationEvents` が空の供給専用拡張機能はこれに依拠している。`undefined` は必ず
   扱うこと: これは **ソフト** 依存なので、実行時チェックとフォールバックを使い、`package.json` の
   `extensionDependencies` に **入れない**(あれは「無ければ動かない」というハード依存であり、
   「あれば使う」を表現できない)。

2. **`fontExt.packageJSON.providedFont` を読み、上記の規則で `{ file, weight }[]` へ正規化する。**
   フォントファイルのパスをハードコードしないこと —— 契約の `file` フィールドはまさにそのために
   あり、消費側が将来のレイアウト変更に追随できるようにするものである。

3. **`fontExt.extensionUri` を webview の `localResourceRoots` に加える。**

   ```js
   const fontExtensionRoots = fontExt ? [fontExt.extensionUri] : [];

   webviewView.webview.options = {
     enableScripts: true,
     localResourceRoots: [
       vscode.Uri.joinPath(context.extensionUri, 'media'), // 自分のルート
       ...fontExtensionRoots,                              // 借用したルート
     ],
   };
   ```

   **これが実際のアクセス制御である。** このルートが無ければ、VS Code は他の拡張機能配下の
   ファイルに対する `asWebviewUri` の URL の配信を、*CSP を評価する前に* 拒否する。逆に、
   一度加えてしまえば **CSP の `font-src` を広げる必要はない**: `asWebviewUri` は借用した
   ファイルを消費側 webview 自身のリソース authority へ書き換え、それはまさに
   `webview.cspSource` が返すものなので、既存の `font-src ${webview.cspSource}` がすでに
   覆っている。(tmux-opener の実機で検証済み。)エントリは自分の拡張機能配下にある必要は
   なく、任意の `vscode.Uri` が受け付けられる。フォント拡張機能が無いときは空配列を加える。

4. **face ごとに `@font-face` を 1 つ注入する。** すべて **同じ** `font-family` の下に置くこと。
   ここでの `family` は **消費側自身のレジストリの** family 文字列であって `contract.family` では
   ない —— 後述「契約の値を安全に注入する」を参照:

   ```js
   // `family` は消費側自身のレジストリ(tmux-opener では FONT_REGISTRY)から来る。
   // 契約から取るのではない。`faces` は手順 2 で正規化したリスト。
   let css = '';
   for (const face of faces) {
     // `.split('/')` は単なる区切りの慣習ではなく効いている: 絶対パスの `file`
     // ('/etc/passwd' -> ['', 'etc', 'passwd']) を拡張機能ルートの外へ逃がさず、
     // ルート相対に解決させる。`vscode.Uri.file(face.file)` や文字列連結では失われる。
     const fileUri = vscode.Uri.joinPath(fontExt.extensionUri, ...face.file.split('/'));
     const fontUri = webview.asWebviewUri(fileUri);
     css += `
       @font-face {
         font-family: '${family}';
         src: url(${fontUri}) format('truetype');
         font-weight: ${face.weight};
         font-display: block;
       }`;
   }
   // .term { font-family: '<family>', monospace; }
   ```

   face どうしの違いは `font-weight` ディスクリプタだけであり、**bold セルがどの face を得るかは
   CSS の font matching の判断であって消費側の判断ではない。** 重みごとに face を自分で選ばない
   こと。`font-display` を face ごとに変えないこと —— face が読み込まれるまで文字を不可視に
   保つのは全 face 一律であり、1 つの face だけ `swap` にすると、一律の値が避けているまさに
   その「見える置換」を許すことになる。

   その `<style>` が置かれる CSP は、借用フォントのために広げる必要はない。tmux-opener の
   基準値は、借用の仕組みが存在する前から変わっていない:

   ```html
   <meta http-equiv="Content-Security-Policy"
         content="default-src 'none'; style-src ${webview.cspSource} 'unsafe-inline'; script-src ${webview.cspSource}; font-src ${webview.cspSource};">
   ```

   `style-src` の `'unsafe-inline'` は注入された `<style>` ブロックに必要なもの。
   `font-src ${webview.cspSource}` はすでに借用ファイルを覆っている —— `asWebviewUri` が
   この webview 自身の authority へ書き換えたからである。これが手順 3 の言う「既存の
   `font-src`」である。

5. **複数の family をレジストリに持つなら、family 名は長いものから照合する。** 登録済みの
   ある family が別の family の *部分文字列* であることがある(`Mgen+ 1mn` は
   `Rounded Mgen+ 1mn` の部分文字列)。素朴な部分文字列判定では Rounded の選択が Mgen+ の
   拡張機能に解決され、誤った package から借用してしまう。

### 契約の値を安全に注入する

**契約は別の拡張機能のデータであり、上記の妥当性規則はサニタイザではない。** 規則が要求するのは
空でない文字列であることだけで、CSS のメタ文字については何も言っていない。400 の解釈に失敗した
値は単に「主張なし」であり、その face は生き残りうる(別の face が 400 を覆う)し、その
`weight` 文字列はそのまま逐語で埋め込まれる。

- **`font-family`: 埋め込むのは自分のレジストリの定数であって、決して `contract.family` では
  ない。** 供給側が宣言する `family` が
  `x'; } body { display: none } @font-face { font-family: 'y` であっても、この文書のすべての
  規則を通る。値は `@font-face` ブロックの **内側** に着地するので、その閉じ引用符が
  `font-family` ディスクリプタを終わらせ、`}` が `@font-face` 規則全体を終わらせ、以降は
  新しいトップレベル CSS として解釈される —— ここでは `body { display: none }` 規則、続いて
  テンプレート末尾の `';` がなお構文として通るように新しい `@font-face` が開かれる。契約の
  `family` は使うためではなくレジストリのエントリと *突き合わせる* ために存在する(「注入機構は
  …依存しない」を参照)のだから、定数を使うことに何のコストもない。
- **`font-weight`: 数値、または空白区切りの数値の対であることを確認してからのみ埋め込む** ——
  400 の規則がすでに述べているのと同じ解釈である。それ以外は通さずに落とすか無視する。
  **tmux-opener はまだこれをしていないことに注意**: `getHtml` は `font-weight: ${face.weight}` を
  逐語で書き出し、`coversWeight400` は 400 被覆の `some(...)` 判定にしか使われない ——
  残りの face の weight は一度も解釈されない。あちらでは信頼境界の議論(供給側は
  `FONT_REGISTRY` にハードコードされた固定の拡張機能 ID である)で受容されているのであって、
  規則が適用されないからではない: **この正本に照らせば、参照実装はこの 1 点で未達である。**
  あのファイルをここでの手本と受け取らないこと。
- **レジストリが保持しうる family 名を制約すること。** 新しいエントリのほうから宣言を破れて
  しまわないようにするためである。tmux-opener は `test/font-registry.test.js` で自身の
  レジストリを `/^[A-Za-z0-9 +-]+$/` に対して表明している。

これで悪意あるフォント拡張機能が無害になるわけではない —— インストールされている時点で
それは拡張機能ホストの中で動く —— が、供給側が消費側の webview の CSS に手を伸ばすことは
防げるし、代償は定数 1 つと正規表現 1 つである。

tmux-opener の `src/font-registry.ts`(解決部。`node --test` で駆動できるよう `vscode` の
import を一切持たない)と `src/extension.ts` の `getHtml`(URI 構築と注入)が、この 5 手順すべての
動く実装である。

## 注入機構はフォントファイル内部の名前に依存しない

`@font-face` は family 名を **宣言する** のであって、読み取らない。消費側は **自分が保持して
いる** family 文字列を `@font-face { font-family: … }` へ埋め込み —— tmux-opener では自身の
`FONT_REGISTRY` のエントリ(`getHtml` の `for (const { family } of FONT_REGISTRY)`)——
**CSS の font matching はファイル内部の `name` テーブルを一切参照しない。** nameID 16 が
まったく別のことを言っている face でも、同じように注入され、照合され、描かれる。

**注入の経路上、契約の `family` はまったく読まれない。** `getHtml` が契約から取るのは `file` と
`weight` だけで、それ以外は取らない。`resolveBundledFontSource` も同様にレジストリを基準に
動き、`providedFont.family` を見ることはない。正確に言うこと —— 反対の主張(「消費側は契約の
値を埋め込む」)はこのリポジトリですでに 3 度なされており、この正本はそれを終わらせるために
ある。

帰結が 3 つあり、どれも読み飛ばしてよいものではない:

- **package README に実測された `name` テーブルの行は、フォントについての証拠であって、
  機構についての証拠ではない。** 2 つの face が 1 つのタイポグラフィ family を共有していると
  記録することは、それらを 1 つの CSS `font-family` に束ねることを *正当化* する(そして
  メトリクスの一致を偶然ではなく期待される性質にする)。注入を *機能させている* ものでは
  ない。
- **契約の `family` は、注入への入力としてではなく、消費側自身のレジストリのエントリと一致
  しなければならない宣言済みの文字列として意味を持つ** —— 規約の両側にある 2 つの宣言である。
  まさに注入で読まれないからこそ、不一致は **無症状** である: 解決も注入も描画もすべて成功
  したまま、2 つの宣言名だけが食い違う。だからこそ機械検査が必要であり、
  `test/font-registry.test.js` が両方向(⊆ と ≡)でそれを持っている。
- **供給側が宣言した文字列を自分の CSS に埋め込むほうが、2 つのうち安全でない側でもある。**
  自分のレジストリが持つ `family` は自分が制御する定数であり、他の拡張機能の `package.json` から
  読んだ `family` はその拡張機能が制御する値である。そして契約の妥当性規則(空でない文字列)は
  CSS のメタ文字を排除しない。消費側の手順の「契約の値を安全に注入する」を参照。

## このディレクトリの package についての作法

以下は `font-packages/*` に対するリポジトリ側の規則であって、契約が第三者の供給側に課す要件では
ない。

- **フラットな別名は常に残す。** `faces` だけの契約(フラットな `file` / `weight` が無い)は上の
  読み手仕様の意味で正当なので、第三者の package はそれを出荷してよい。それでも **この**
  リポジトリの拡張機能は、400 を覆う face とバイト単位で等しいフラットな対を常に `faces` と
  並べて宣言する。古い読み手で動く消費側でも使える regular face を得られるようにするためである。
  その機械的な檻が `test/font-registry.test.js` であり、その等価性ガードが、`faces` 配列がある
  場合には必ず `providedFont.file` / `providedFont.weight` を 400 を覆う唯一の `faces` エントリに
  対して表明する。
- **1 フォント 1 拡張機能。** 各 family は独立にバージョン管理される専用の拡張機能
  (`{publisher}.font-{slug}`)から供給され、複数のフォントを抱えた 1 つの拡張機能からは供給
  されない。理由は à la carte のインストールと独立したバージョニングであり、「消費側の VSIX を
  肥大させない」が単に「肥大した pack」へ移動するだけになってはならない。
- **package の `version` はそれが公開するバイト列を名指すものであり、bump の理由はその bump を
  もたらす変更の中に書き記す。** bump が答える問いは「この package が公開するものは、前の
  バージョン番号で公開されたものと違ったか?」であって、「bump を運んだ差分がどれだけ大きかったか」
  ではない。後者は別の問いであり、たいてい小さい方の問いである。書き記さなければならないのは、
  2 つの答えが日常的に食い違い、そして後からその意図をリポジトリの中から再構成できるものが
  何も無いからである。実例、#289: `font-mgenplus-1mn`・`font-rounded-mgenplus-1mn`・
  `font-mplus1code` は **0.1.0 → 0.2.0** へ上がったが、その変更が編集したのは README だけだった。
  bump は README のためではない —— **6 つの TTF** のためである。そのすべてが 0.1.0 として公開
  されたバイト列と異なっており、それは #291(`fitRatio`)と #293(`vstretch`)が焼き直したのに
  どちらもバージョンに触れなかったからである。patch ではなく minor なのは、焼き直された輪郭は
  ユーザーが画面上で見て分かる変更であり、バージョンだけから読み取れることに意味がある唯一の
  変更種別だからである。`font-plemoljp-console` は同じ変更の中で **0.0.1** に留まった —— 無改変
  regime であり、焼き直しは届いておらず、出荷バイト列はすでに公開済みのものである。文書だけの
  再公開(TTF はそのままで Marketplace の Readme / License タブを訂正する)は、同じ理由で patch
  bump になる。**理由を書く前に実測すること**: 面ごとに、`git show <commit>:<path> | sha256sum` を
  現在のファイルと突き合わせる、それが確認のすべてである —— 上記 3 package に 0.1.0 を設定した
  コミットは `3bfd558`。
- **どの package もちょうど 2 つの取得元 regime のいずれか 1 つに属し、どちらであるかは判断では
  なく事実である: `scripts/font-fit/manifest.json` に載っている package は変換出力を出荷し、
  載っていない package は上流のバイト列を無改変で出荷する。** あのファイルは変換パイプラインの
  仕事一覧なので、載っていることと「変換された」ことが乖離しようがない。2 つの regime は
  **異なる** 主張をし、異なるやり方で証明される —— 無改変 regime には二列 sha256 表、変換 regime
  には三段連鎖 —— そのどちらも以下に規定する。フォントを追加するとは、まずどちらの regime かを
  決めることである。
- **無改変 regime の package はフォントを配布されたままバイト単位で配置する。** ファイル名も
  元のまま —— 名前を変えたり subset したりすれば、何の利益も無いのに OFL §5 のようなライセンスの
  派生物規定の下に package を置くことになる —— 配布物自身のライセンスと README を、archive 内部の
  パスのまま並べて出荷する。
  - **例外 —— 配布 archive が自身のライセンスや README を持たない場合。** リリースによっては
    フォントファイルだけを出荷しており(PlemolJP の zip はライセンスと README のエントリを 1 つも
    含まない)、並べて置くものが存在しないので上の条項をそのままでは満たせない。その場合は
    **上流リポジトリの、そのリリースに対応するタグ** から一次ライセンス文書を取り、package へ
    取り込み、取得したすべての文書を package の取得元に記録する。**それ自身のファイルとして
    出荷される文書は、TTF と同じ 2 つの実測列を得る**: `取得元 URL | sha256(取得時)` を配置前の
    ダウンロードファイルで実測し、`配置先 | sha256(配置後)` を配置後のファイルで実測する。
    そうした文書も他と同じく出荷バイト列なので、2 列が存在する理由 —— 配置後のファイルだけを
    実測して数値を両列にコピーすると、そのファイルを自分自身と比較することになり何も検証
    しない(「取得元 regime 1」を参照)—— がそのまま当てはまる: **配置されたファイルが存在する
    ときは、行を 1 列に潰さないこと。**

    **引用によって取り込まれた文書は代わりに `—` を得て、どこへ行ったかを名指す。** package の
    `LICENSE.txt` は *組み立てられる* ことがあり(OFL 本体に、`name` テーブルが持つ著作権表示の
    行を足す)、そこへ逐語で引用された取得文書にはハッシュを取るべき配置ファイルが存在しない:
    `配置先` を引用箇所(例 `LICENSE.txt に逐語で引用`)、`sha256(配置後)` を `—` と書く。
    その行は潰された 2 列の行ではない —— 上の禁止は *ファイル* についてのものであり、1 つの
    ファイルを 2 度ハッシュすることが自己比較になる、という話である。代わりに、引用が取得文書と
    バイト単位で一致することを確認した旨を記録する。それが右の列が担うはずだった主張と同じ
    ものである。

    この例外は付随文書についてのものだけであり、フォントファイル自体のバイト単位の規則は
    変わらない。ライセンスと README を *持っている* archive は上のとおりに扱う。PlemolJP
    Console HS の package がこの経路をとった最初の例である。
- **family 名は想定ではなく実測である。** package の README は、出荷する **各** face について
  `fc-scan`(または同等のもの)が読み取った値を記録する。その実測が記録するのは変換が *書いた*
  名前であり、そもそもその名前をどう **選ぶ** かは次節である。

### 出荷する family 名の導き方

**この節は変換された package が出荷する名前を決める。これは命名の規則であってライセンスの規則
ではない** —— 後述の予約フォント名の確認は別個の、より厳しい制約であり、この規則が出した名前を
拒否しうるし、この規則が何を言おうと必ず走る。独立した 2 つの問いを、この順で問う。

```
<上流の family 名> + " Term"
```

- **` Term` は変換出力の印** であり、バイト列についての特定の 2 つの事実を意味する: 幅 1 の
  符号位置がちょうど 1 セル分送ること、**かつ** そのインクが、このディレクトリの契約が定める
  意味でセルに収まっていること(「端末の幅の規約」を参照)。**変換されていない package は決して
  これを取らない** —— `PlemolJP Console HS` は上流のバイト列を上流の名前で出荷する。したがって
  この接尾辞と `scripts/font-fit/manifest.json` への所属は同じ事実を 2 度言ったものであり、
  package がどちらの取得元 regime(三段連鎖か二列 sha256 か)にあるかはその名前から読み取れる。
- **上流のバリアント語は残す —— ただし ` Term` がすでに担っている意味の語は除く。** 決め手は
  **意味** についての問いであり、機械的なテストではなく判断である: **その語は ` Term` が主張する
  性質と同じことを主張しているか** —— 幅 1 の符号位置がちょうど 1 セル分送り、そのインクが
  そのセルの内側にある、という性質を。そうであれば 2 つは同じことを 2 度言っているので語は落ちる。
  別のこと —— *どの書体か*、あるいはセル幅と直交する軸 —— を言っているなら残る。

  | 上流 | 語 | その語が言っていること | ` Term` がすでに言っているか | 判定 |
  |---|---|---|---|---|
  | `HackGen Console` | `Console` | 対になった 2 つのうち端末向けの側だという上流の印 —— 記号をセルへ寄せてある | **はい** | **落とす**: 出荷名は `ShirokumaGen Term` |
  | `M PLUS 1 Code` | `Code` | *どの書体か* —— プロポーショナルな `M PLUS 1` の等幅の兄弟である | いいえ | **残す**: `M PLUS 1 Code Term` |
  | `Mgen+ 1mn` と `Rounded Mgen+ 1mn` | `1mn` | この family のどのカットかという上流の指定(重みは別トークン —— `scripts/font-fit/manifest.json` の `mgenplus-1mn-regular.ttf` / `-bold.ttf`)。中の `m` は上流の等幅の印(上流自身の命名であり、ここで実測したものではない) | **半分だけ** | **残す**: `Mgen+ 1mn Term` / `Rounded Mgen+ 1mn Term` |
  | `PlemolJP Console HS` | — | — | — | **対象外**: この package は変換されていないので ` Term` を一切取らず、どの語が重複しうる接尾辞も存在しない。上流のバイト列を上流の名前 `PlemolJP Console HS` で出荷する(実測: 出荷する両 face の nameID 1) |

  **部分的な重なりでは語は残る。** ` Term` は *2 つ* の事実(1 セル分の送り、**かつ** そのセルの
  内側にインクがあること)を主張するので、語はその一方だけを言っていて重複にならないことが
  ありうる。それが `1mn` の行である: 等幅は 1 つめの事実だけであり、`1mn` は 2 つめを何も主張して
  いない —— それは #275 の変換がそれらの face のために *作り出さねばならなかった* 主張であり、
  両 face とも出荷時点ではセルの契約を満たしていなかった(「選定時の実測」を参照。そこに記録
  されている不合格は 1 つめの事実についてのもの —— 9 つの探針すべてで全角送り —— なので、変換は
  両方を作り出さねばならなかった)。落としてしまえば、このバイト列が `Mgen+` のどのカットで
  あるかも消える。接尾辞と重複するのは **両方** の事実を言う語だけであり、だからこそ今のところ
  落ちたのは `Console` の行だけで、それが出荷名と一致している。

  **「語を取り除いて、残った名前を上流が公開しているかを問う」は傍証であって手順ではない** ——
  手順として書き下さないこと。問う価値はあるし、*豊かな* 形なら実際に働く: 「残ったものは同じ
  書体の兄弟バリアントか、それとも別の書体か?」は最初の 2 行を正しく分ける —— `HackGen` は
  HackGen Console の兄弟であり、`M PLUS 1` は別の、プロポーショナルな family である —— 兄弟が
  見つかればその語は 1 つの書体の *処理* を名指していたと示唆され、別の書体が見つかればその語は
  書体を名指していたと分かるからである。それでも 2 つの理由でこれは検査ではなく傍証に留まる。

  **yes / no に潰すと何も決められない。** 「残った名前を上流が公開しているか?」は `HackGen` にも
  `M PLUS 1` にも **はい** と答え、両者の判定は逆である。*機械的* な検査は実際にはその形で
  書かれることになり、その形では答えは 2 つを分けるものになりえない。情報はすべて、より豊かな
  「それは何か」の読み方の側にあり、そちらはすでに参照ではなく意味についての判断である。

  **そして豊かな形でもなお `HS` を間違える。** `PlemolJP Console HS` から `HS` を取り除くと
  `PlemolJP Console` が残る —— 同じ書体の別バリアントなので、傍証は「落とす」と言う。意味の問いは
  これを残す: `HS` は上流のリリースバリアントの印で **"Hidden Space"** ——既定リリースが持つ
  表意文字空白の可視化を **加えない** カット —— を表す(どの archive から来たかとともに
  `font-plemoljp-console/README.md` に記録されている)。これは、幅 1 の符号位置が 1 セル分送るか、
  そのインクがどこに落ちるかとは何の関係も無い軸である。**この 1 行が傍証の問いを格下げした**
  —— 2 つが食い違う唯一の事例である —— そして今日は何も決めない。規則は変換されていない package に
  届かないからであり、上の表のその行に判定が無いのはそのためである。これは、直交するバリアント語を
  持つ次の package がぶつかることになるものである。

  **どのセルを、どのファイルの上で実測したか、そしてそれがどれだけ再現可能かを書くこと**(#298)。
  **3 つの上流ファイルのいずれも今日このリポジトリの作業ツリーには無い**: HackGen の 2 face は
  ここに同梱されたことが一度も無く、`MPLUS1Code.ttf` は 2 度同梱されて 2 度削除された ——
  #199(`f809787`)で `media/fonts/` から、#275(`3bfd558`)で
  `font-packages/font-mplus1code/fonts/` から。後者はそれを変換出力で置き換えたコミットである。
  以下の「実測」はすべて作業ツリーの外にあるコピーの上で取られたものであり、2 つの行は
  **異なる経路** で再取得できる。同じ経路の程度差ではない:

  | 上流ファイル | その上で実測したもの | もう一度そのファイルを得る方法 |
  |---|---|---|
  | `HackGen-Regular.ttf` と `HackGenConsole-Regular.ttf`、どちらも `HackGen_v2.10.0.zip` から | `name` テーブルは `HackGen` と `HackGen Console` と読め、**両者とも ASCII 印字可能文字 0x21–0x7E をすべて同じ 540 ユニットで送る** —— 2 つの書体ではなく、1 つの等幅書体の 2 バリアントである | **取得することによって、そして取得によってのみ**: どちらの上流ファイルもこのリポジトリで追跡されたことが一度も無い(`git log --all --diff-filter=A --name-only` は HackGen の face を 1 つも挙げない)。出荷中の `ShirokumaGenTerm-*.ttf` はその代用にならない —— 確かに上流の輪郭は持っている(`font-shirokumagen/README.md` が契約②、面ごとに 13,101 個中 0 個のボディグリフが変化と記録し、`LICENSE.txt` はそれを根拠に書かれている)が、送り幅は変換後であり名前も違うので、それは変換の出力であってこの行が対象としているファイルの複製ではない。`manifest.json` は archive の `url` と `archiveSha256` を記録しているので、ダウンロードしたコピーを *検証* することはできる —— ただし再取得できるかはそのリリース資産がなお配信されているかに依存する。Console の face には加えて face ごとの `srcSha256` がそこにあるが、素の `HackGen` は自身のエントリを持たないので archive のハッシュを通じてしか固定されていない |
  | `MPLUS1Code.ttf` | `name` テーブルは `M PLUS 1 Code` と読め、これも等幅(500)である | **このリポジトリ自身の履歴から、決定的に** —— 3 つのうち最も強く、しかも manifest 経由ではない: `git show 3bfd558^:font-packages/font-mplus1code/fonts/MPLUS1Code.ttf \| sha256sum` は `ff68678c…fd36` を返し、これはまさにこの package の両 face について manifest が記録する `srcSha256` である(実測。#199 で削除された blob も同じハッシュを持つ)。*再取得できない* のはそれが入っていた上流の **archive** のほうで、そのエントリの `url` と `archiveSha256` はどちらも `null`、理由は `unrecorded` フィールドにある |

  **ここで実測していないこと**: `M PLUS 1` が別のプロポーショナル family であること。そのファイルは
  このリポジトリに一度も入ったことが無く、あの行は上流自身のカタログに拠っている。このリポジトリが
  *読める* のは変換の **出力** のほうで —— `MPLUS1CodeTerm-Regular.ttf` の nameID 1 は
  `M PLUS 1 Code Term`(実測)で、この規則が残した `Code` を持っている —— しかしそれは規則が
  *生み出した* 名前であって、規則が問うた上流の名前ではないので、それ自体では何も裏づけない。

  **もう 1 つ実測したことがあり、それは表の判定を変えない。** 上流の `HackGen Console` の face は
  このディレクトリのセルの契約を **満たさない** ——「選定時の実測(上流候補の評価)」の HackGen
  Console の行を参照 —— それが、無改変で同梱するのではなく変換した理由である。したがって
  `Console` と ` Term` は **保証** において異なる: `Console` はその性質を主張し、` Term` は
  *これらの* バイト列についてそれが成り立つという実測済みの主張である。両者は **何を言っているか**
  においては異ならず、表の列が問うているのはそれだけである: `Console` は ` Term` が言うことと
  同じことを言っている、ゆえに **はい**、ゆえに「落とす」。保証は第二の意味ではないので、それが
  語を救うことはない —— 2 つの文を並べて読めば、食い違いは見かけだけである。
- **基底の名前を変えるのは予約フォント名がそれを禁じるときだけ**(`HackGen` → `ShirokumaGen`;
  OFL 1.1 §3、`scripts/font-fit/check-license.py` で実測 ——「予約フォント名の確認」を参照)。
  上のバリアント語の規則はこの置換で変わらない: それは基底が差し替えられる前の *上流* の名前に
  ついて問われる。
- **我々自身の将来の軸は ` Term` の後ろに積む**(`… Term NL`)。接尾辞が「上流がその face を
  何と呼んだか」と「我々がそれに何をしたか」の境界であり続けるようにするためである。
- **これを間違える代償が安いのは最初のリリースの前だけである。** 出荷済みの family 名はユーザーの
  `settings.json` の中の値であり、その後で変えることは決して取り除けない恒久的な別名エントリ
  (`FontRegistryEntry.aliases`)を代償にする。名前は package を追加する変更の中で決めること。
  #298 が 1 つの family(`ShirokumaGen …`)の名前を変えたのは、まさにまだ公開されていなかった
  からであり、その理由で別名を **取らなかった**。

### 取得元(provenance)regime 1(無改変)—— 二列 sha256 表

**これは `scripts/font-fit/manifest.json` に載っていない package のための regime であり、
過去の遺物の節ではない**: `font-plemoljp-console` が今日ここにいて上流の TTF をそのまま出荷して
いるので、以下の規則は現役である。同じ規則が、**変換された package の付随ライセンス文書・README**
にもそのまま適用される —— それらは隣の TTF に何が起きたかにかかわらずバイト単位で配置される
ものだからである。

各 package は、出荷するバイト列を **2 つ** の実測ハッシュ列を持つ表に記録する:

| アーカイブ内エントリ | sha256(エントリ・展開時) | 配置先 | sha256(配置後) |
|---|---|---|---|

- **左** の列は archive のエントリのハッシュを **ファイルをリポジトリへ配置する前に** 実測した
  もの —— scratch ディレクトリ上の展開済みファイルから取る。**右** の列はその後、配置された
  ファイルの上で実測する。
- **配置後のファイルだけをハッシュして数値を両方の列にコピーしても、何も検証しない**: それは
  配置後のファイルをそれ自身と比較しているだけであり、主張されているもの(「配布物とバイト単位で
  同一」)は *archive* についての主張である。独立に実測された 2 列が一致することが、その行を
  証拠にする。
- 規則は **行ごと** であり、後から追加された face についても元からある face と同じだけ成り立つ:
  新しい face の左列は展開時に実測したエントリのハッシュであって、右列の複製ではない。この規則が
  ここに書かれているので、package はこれを再掲する必要も個々の行に注記する必要もない —— ある
  package の表にあって別の package の表に無い説明的な注記は、実際には無い差が package 間にあるかの
  ように読めてしまう。

### 取得元(provenance)regime 2(変換出力)—— 三段連鎖

**これは `scripts/font-fit/manifest.json` に載っている package のための regime** である ——
今日は `font-mgenplus-1mn`・`font-rounded-mgenplus-1mn`・`font-mplus1code`・`font-shirokumagen`
であり、その TTF は配布されたまま配置されるのではなく端末のセルに合わせてリフィットされている。

**二列の規則はここへ持ち越せないし、無理に伸ばせばそれは偽造になる。** あの規則の主張は
「配布物とバイト単位で同一」であり、*同じ* バイト列の 2 つの独立した実測によって証明される。
変換されたファイルは上流が公開したどれとも同一ではないし、比較相手になるはずのファイル ——
上流の TTF —— はこのリポジトリから意図的に外してある(設計 #271 は上流 TTF を fixture として
コミットすることを検討し、退けた: それは #199 が得たサイズ削減を帳消しにする)。出力のハッシュを
両方の列に書けば、ファイルをそれ自身と比較することになる: 二列の規則がまさに禁じている空の主張
である。

代わりに置かれるのは **別の** 主張であって、同じ主張の安い版ではない: **入力がどこから来たか・
何がそれを出力に変えたか・出力が何のハッシュになったか** —— 3 つのリンク、それぞれ実測され、
どれもここのどの機械によっても上流と突き合わせられない。

**それを運ぶ節の見出しは固定されており**、package の README(英語)はそれをそのまま書く:

```
## Provenance (upstream archive → conversion → output)
```

**この文字列はスタイルの好みではなく機械のキーである。** #276 以降、`test/font-cellfit.test.js` の
manifest と package の等価性検査がこれで照合するので、manifest に載っていてこの節を持たない
package —— あるいは言い換えられた見出しの下に持つ package —— は無音の穴ではなく失敗になる。
**したがってこの文字列を変えてよいのは、テストを変えるのと同じコミットの中だけである。**
分ければ、一方はもう他方が書かない見出しに対して通っていることになる。(無改変の package は素の
`## Provenance` 見出しのままである。矢印の形が変換 regime の印である。)

> **ここから先(Link 1 / Link 2 / Link 3 の内容、再現性の主張の強さ、機械層が何を検証し何を
> 検証しないか)は日本語版に無い。** 英語版 `font-packages/README.md` の同節を参照すること。
> 訳していないのは、その大半が実測値(スクリプトの sha256・ツールのバージョン・面ごとの
> リフィット件数・`fitRatio` と `vstretch` の値・検査の判定式)であり、複製すれば実測値が
> 2 箇所に分かれるからである。
